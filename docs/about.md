# where_is_it (ArtNearby) — документація проєкту

## Про проєкт

Сайт для пошуку матеріалів для малювання поруч з тобою. Магазини й компанії самі додають свої точки продажу й товари, а користувач шукає, де конкретно поблизу є потрібний йому товар для малювання, і як туди дістатись.

Головна задача проєкту (формулювання автора): користувачі мають знайти оптимальний шлях до магазину з потрібними речами для малювання — бо десь товару може не бути, хтось любить ходити за покупками фізично.

## Ролі користувачів

- **Індивідуальний користувач** — шукає товари й магазини поблизу.
- **Компанія / магазин** — реєструється як юрособа, додає свої точки (Store) і товари (Product), керує ними (edit/delete).

## User flow: індивідуальний користувач

1. Користувач реєструється (фізична особа).
2. На головній бачить випадкову підбірку товарів ("Some products that might be interesting").
3. Переходить у повний список товарів, фільтрує за категорією.
4. Відкриває картку товару.
5. Тисне "Find the shortest way to the shop!" → бачить магазини поруч, відсортовані за відстанню, з можливістю прокласти маршрут. **(ключова фіча, ще не реалізована — див. нижче)**

## User flow: компанія

1. Компанія реєструється як юрособа (вказує назву компанії, адресу, телефон, tax ID).
2. Логіниться, заходить у профіль.
3. Переходить у "Manage my stores" → додає свою точку продажу (Store).
4. Переходить у "Manage my products" → додає товари (Product), прив'язуючи їх до свого магазину й виробника (Fabricator).
5. Редагує/видаляє свої товари та магазини за потреби.

Доступ до кроків 3-5 гейтиться на рівні ролі (`user_type == 'company'`) — див. секцію [Access control](#access-control-acl) нижче.

Живий статус реалізації кожної фічі та відомі технічні проблеми винесені окремо, бо оновлюються частіше за цей документ:
- [`docs/roadmap.md`](./roadmap.md) — що готово / в процесі / заплановано.
- [`docs/known-issues.md`](./known-issues.md) — актуальні баги.

## Access control (ACL)

Доступ до management-функцій (додавання/редагування/видалення Store і Product) перевіряється на трьох рівнях:

1. **Автентифікація** — `LoginRequiredMixin`: треба бути залогіненим.
2. **Роль** — `company_required` (`find_it/decorators.py`): треба `Profile.user_type == 'company'`. Незалогінених редіректить на `login`, індивідуальних користувачів — на `index`.
3. **Власність** — `UserIsOverMixin` (`find_it/mixins.py`): перевіряє, що `instance.creator == request.user`, тобто компанія може міняти лише свої магазини/товари, а не чужі.

⚠️ Рівень 3 застосований **не всюди**: коректно лише на `ProductDeleteView`. `ProductUpdateView`, `StoreUpdateView` і `StoreDeleteView` перевіряють лише роль (рівень 2), без перевірки власності — деталі й наслідки в [`docs/known-issues.md`](./known-issues.md).

## Технічний стек

- Backend: Django 6.0.4 (потребує Python ≥3.12), gunicorn, whitenoise
- БД: SQLite (dev); Docker Compose є (web-сервіс), окремий сервіс БД і seed-дані — заплановано
- Карти: MapTiler SDK (обрано замість Google Maps — безкоштовний тариф без картки)
- Зображення: Pillow
- Деплой: Render.com, Docker

## Модель даних (спрощено)

- `User` (Django auth) 1—1 `Profile` (тип: individual / company, дані компанії)
- `Store` (назва, опис, телефон, сайт, creator) 1—N `Location` (адреса, місто, координати)
- `Store` 1—N `Product` (назва, категорія, ціна, опис, зображення, creator)
- `Product` N—N `Fabricator` (виробник) — під питанням, чи не мало б бути N—1, див. [`docs/known-issues.md`](./known-issues.md)
